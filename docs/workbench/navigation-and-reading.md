# Workbench navigation and reading

The Workbench Plugin owns layout preferences and completed-reply read positions. It does not own Session execution, Interaction validity or authentication. Default pages are assembled through the same public UI contracts available to independently installed packages. `apps/web` remains an inert bootstrap/access/error boundary.

## Pending and unread are independent

`interactions.pendingIndex` is an authenticated owner snapshot with an exact `count`, up to 50 lightweight `items` (`id`, `sessionId`, `kind`, `title`) and an optional `next` cursor. Its complete serialized summary DTO has an explicit 96000-byte budget under the unchanged 100000-byte transport registration. JSON-escaped UTF-8 item bytes, commas and the fixed UUID continuation frame are charged before an item is emitted. Normal short titles retain 50-item pages; legal long/escaped titles may produce fewer items, with `next` always identifying the last emitted request. Pass `after` to continue, and follow `next` rather than inferring completion from page length. The exact count and all full titles remain unchanged; no request is skipped or truncated to fit. It includes only current-Host pending permission requests and native work forms. Responding, terminal, expired and invalidated channels and ordinary chat never enter it. `interactions.request {id}` reads an exact selected request independent of the bounded history cards. Responses still use the Interactions owner's commands, CAS, current native-channel generation and immutable command receipts.

The Workbench resolves up to 50 owned Session navigation references through `sessions.references {ids}`. All requested owned IDs and their Workspace linkage are retained under the unchanged32768-byte cap. Each navigation label is limited to256 serialized UTF-8 JSON bytes without splitting valid Unicode points; `nameTruncated:true` explicitly identifies a compact label. Ordinary short names remain unchanged with no flag. Full immutable names remain available through the authenticated, owner-scoped `sessions.detail {id}` resource; the default pending view discloses compact labels before linking by exact IDs. That snapshot is separate from the Interactions snapshot: the composed screen does not claim a shared owner watermark. Hiding `workbench:pending-link` or replacing a menu only changes presentation, never the count or response authority.

Sessions appends a `CompletedReplyFact` to its opaque `replyFacts` source in the same transaction that first projects a live completed Turn with actual Agent text. The source discriminator is `live-completion`. Native history replay must never append this fact; recovery remains ticket 23. No timer or ordinary question infers completion. Workbench consumes the source using its own durable offset, records a per-reply row and publishes a Workbench invalidation when the projection commits.

`workbench.unread` returns the exact unread `count`, up to 50 reply summaries and an optional `next` cursor; `after` continues the page. Read position is a set of exact opened reply IDs, not a global event sequence, maximum Session activity or wall clock. `workbench.markRead {sessionId, activityIds}` validates that every reply belongs to the principal and Session before acknowledging any. It never includes a later reply implicitly. A projection which is not ready returns `REPLY_UNAVAILABLE`; the view retains and retries the same intended command/IDs when Workbench synchronization advances.

The public `aork.workbench.read-tracker@1` wrapper accepts `ReadTrackerContext` from `@aork/contracts/workbench`: exact `sessionId`, `activityId` and rendered `content`. Mount it inside a successful message renderer around the complete corresponding reply. It acknowledges only while that content intersects the visible viewport, the document is visible, the wrapper is exposed by current hit-testing, and its own ancestry is not inert, hidden, `aria-hidden`, transparent or CSS-hidden. Native `showModal()` and rendered ARIA modal surfaces block outside content without requiring a marker. A single scoped presentation observer rechecks semantic/DOM changes, scrolling, resizing and layer removal; uncovering does not require another reply/domain event, and an uncovered reply still offscreen remains unread. A failed/replaced/hidden/unmounted message view cannot acknowledge content it did not render. The tracker reports a local synchronization error while preserving readable content. A public caller may reuse one mounted tracker slot and change its Session/activity context; no key/remount convention is required. Each committed immutable payload generation has its own command ID and in-flight/retry state. Same-payload retries retain that ID, while a new context receives a new ID. Layout-effect cleanup fences the previous generation at the context commit, and every asynchronous completion, failure, retry and finalizer checks its live generation before changing local state or disposing observers. A late old result cannot complete, unlatch, block or display an error for a newer reply.

Independent layouts must report their owned covered-content scopes truthfully. The narrow public presentation marker `READ_VISIBILITY_ATTRIBUTE` is `data-aork-read-visibility`; set its value to `covered` on the affected content scope while an opaque non-hit-tested layer (for example `pointer-events:none`) covers it. The tracker checks this marker only through its own ancestry, alongside standard `inert`, `aria-hidden`, CSS and modal semantics. Removing the marker is not a read operation: the actual reply must also be in view and exposed. This is not server authority or a generic SDK business-state channel. Unannotated decorative overlays which bypass hit-testing cannot be inferred reliably across browsers; their owning layout must expose the covered scope. No private layout IDs, classes, component-tree inspection or renderer-commit signal counts as seeing content.

Compact `sessions.timeline` exposes `completedReplies` only when all owner Agent chunks for that reply are actually included, untruncated, in the rendered timeline. Retaining a Turn status or input preview is insufficient. `sessions.reply {turnId, after?}` reads the immutable completed response in bounded pages (up to 50 chunks and a byte budget); its `next` is a chunk sequence. The default `#reply=<activityId>` view opens that reply alone and mounts the tracker only after all its pages have been explicitly expanded. Querying a summary or merely visiting the unread list does not clear anything.

## Public composition

The default workbench is three regions. Each region has a replaceable container contract and its own multi-plugin extension targets, so a plugin can add to one region without replacing the layout or any other region.

| Region | Container (one selected provider) | Extension targets | Default content |
| --- | --- | --- | --- |
| Left | `aork.workbench.sidebar@1` | `aork.workbench.navigation@1`, `aork.workbench.rail-sections@1` | Brand, New Session/Pending/All workspaces, `aork.workspace.navigation@1`, `aork.sessions.navigation@1`, then installed rail sections |
| Centre | `aork.workbench.header-view@1` and `aork.workbench.main@1` | `aork.workbench.header@1`, `aork.workbench.toolbar@1`, `aork.workbench.conversation@1` | Session header, installed conversation band, then the active page |
| Right | `aork.workbench.inspector@1` | `aork.workbench.inspector-tabs@1` | The default docking shell (tab strip, start page, splits, floats) with four panel types — Files, Terminal, Browser and Preview; each extension declares one openable panel type |

| Other surface | Selected contract |
| --- | --- |
| Complete layout | `aork.workbench.layout@1` |
| Home, pending, unread | `aork.workbench.home@1`, `aork.workbench.pending@1`, `aork.workbench.unread@1` |
| Workspace navigation and page dispatch | `aork.workspace.navigation@1`, `aork.workspace.page@1`, `aork.workspace.workspace-page@1` |
| Session navigation/create/header/detail/actions | `aork.sessions.navigation@1`, `aork.sessions.create@1`, `aork.sessions.header@1`, `aork.sessions.detail@1`, `aork.sessions.actions@1` |
| Session children | existing messages, tools, composer, permission cards/form and structured cards/form contracts |
| Files | `aork.workspace.files@1`, contributed by the workspace plugin into the right region rather than hard-coded by the layout |
| Terminal, Browser, Preview | `terminal:terminal`, `browser:browser`, `preview:preview`, panel types on `aork.workbench.inspector-tabs@1`; the Terminal's contract is in [Terminal panel](terminal.md) and the Preview's in [Workspace files](../workspace/files.md) |
| Menus, notifications | `aork.workbench.menu@1`, `aork.workbench.notifications@1` |

The left region shows the Workspace list and the Session browser as sibling sections: `aork.workspace.navigation@1` owns Workspaces only, and `aork.sessions.navigation@1` is the dsh-style session browser — grouped by Workspace or flat, ordered by last update or by manual drag (dragging a row switches the view to manual order and persists it through `sessions.reorder`), with pinning, rename, context handoff, an expanding search and per-group watermark pagination. There is no archive entry in this surface; the backend archive command stays dormant. The right region is defined by `aork.workbench.inspector@1`; the layout still owns that region's close and wide controls, so replacing the container provider never removes the way to close it. The default provider presents a docking surface: the tab strip is the region's top edge, the guide page lists every installed `aork.workbench.inspector-tabs@1` panel type (a single registered type seeds itself directly), panes can split, tabs can drag between panes or float outside the region, and the whole layout persists per Session in `localStorage` (`aork.inspector.v1.<sessionId>`). Git changes are not a placeholder tab: a Git plugin contributes its own right-region panel type when installed.

### Right-region panels

**Panel types.** Each is an ordinary extension on `aork.workbench.inspector-tabs@1`, ordered by `order`, and a profile hides or reorders it through `ui.extensions` like any other. The manifest may give a type a `label`, an `icon` (a semantic ID the selected icon provider resolves), a one-line `description` for the start page, `multiple: true` when every open is a tab of its own, and `opensWith` — the selection key whose presence opens it.

**The default page.** A docked region never stays empty. With exactly one installed type that type opens itself; with none or several, the start page shows one capsule per type in the profile's order. The start page is a doorway rather than a page that stays open: picking a capsule opens the type as a tab in its place, and it always yields — even when what was picked is already open elsewhere and is only revealed — unless it is the region's one tab, which nothing closes but the region's own control. Closing the last tab returns the region to its default page rather than leaving it empty; this differs from dsh and is a local decision with tests of its own.

**Instances.** A type with `multiple: true` opens a tab per piece of content and reads its identity from `tab.content`: the region mints one for a tab opened without, and a link names one. Tabs of one such type are told apart by content, so opening content that is already open reveals it instead of adding a tab. A type without it holds one instance for the whole region and is focused where it already shows.

**Links.** A selection key named by a type's `opensWith` — `file` for Files, `preview` for the Preview — opens that type in place of a start page showing alone. A multi-instance type opens the link's content once; a later link naming content that is already open brings its tab forward. The link stays in the address, so it is answered when what it names changes, not whenever the region renders.

**What a panel body is given.** `InspectorTabContext` (`@aork/contracts/workbench`) is the layout context plus `tab`:

- `id`, `sessionId`, `kind`, `content?` and `floating` say which tab this is. `id` is stable for the tab's life and `content` is saved with the Session's layout.
- `signal` is aborted when the tab closes and at no other time. It is a body's cue to end what it owns — a page, a process — and to drop what it kept. A switch to another tab, a collapsed region and a change of Session unmount the body and abort nothing: what must outlive them lives outside the component, keyed by `tab.id` or `tab.content`, and is dropped on the signal.
- `open(trigger, content, { replace? })` opens `content` with every installed type that declares `opensWith` as `trigger`, in this tab's pane unless the tab floats. A caller names the trigger and never another plugin's ID; nothing happens when no type declares it. With `replace`, a tab lending its place gives it up only to content that was not open before — what is already showing is revealed where it is, and the tab that asked stays.
- `close()` closes the tab, and `setTitle(title)` is what its chip reads from then on; the title is saved with the layout.

The context is presentation only and is recreated on layout renders, so effects key on the tab's identity rather than on the object. A body is one tab — the region keys it by `tab.id` — and never has to follow another. A body whose root carries `data-dock-fill` fills a floating window instead of taking its natural height and scrolling.

**The strip.** A secondary press on a chip opens its menu — 关闭, 关闭其他 and, while tabs sit to its right, 关闭右侧; Escape closes the menu and hands focus back to the chip. A middle click closes without selecting. A strip holding more tabs than fit fades the chips it hides at either end, keeps its controls in place and scrolls the active chip into view; a vertical wheel over the chips scrolls the strip. Revealing a tab that is already on screen changes nothing visible by itself, so its pane glows once. Splits are side by side, never more than two, and the whole layout — panes, tabs, what each shows, its title, floats and fullscreen — persists per Session in the browser and never crosses devices.

The desktop regions start at the top of the workbench. In an embedded Session detail, the transcript scrolls above the docked composer. The desktop right separator adjusts the width by dragging or with the arrow keys. This adjustment lasts for the current page, and the regular and wide presets continue to persist across reloads.

`UiRuntime.renderView(contract, context?)` and `renderExtensions(target, context?)` transport an unknown, versioned business context without exposing private components or query-library state. `WorkbenchLayoutContext` publicly defines presentation preferences, a `save(update)` callback, a narrow-layout flag and an `inspectorOverlay` flag that tells region providers the right column is currently a compact drawer. Session detail accepts `{embedded:true}` to omit its own header when the selected Workbench header mounts the independently replaceable Session header. Independent layouts must retain the child slots they promise, rather than importing private default components. Contextual Artifact preview/actions are added by the Artifact tickets; there is no standalone Artifact navigation.

Navigation, header, toolbar, menu items, notification sources, rail sections, conversation bands, inspector panel types and Settings sections use declared extension IDs. Existing profile `order` then stable qualified ID determines order; `hidden` removes only presentation. Theme tokens and semantic icons continue through the selected public theme/icon providers. The default Layout changes only its own selected `workbench:theme`; an independently selected theme retains its own tokens and scheme policy. A local view failure identifies the selected provider and contract, preserving sibling providers, saved history and server authority. Profile composition remains explicit and requires a fresh graph/authentication; no last-registration-wins or live module patching is introduced.

## URL and preferences

The URL retains `workspace`, `session`, reply, file/directory/line and unrelated extension keys. `page=pending|unread|workspaces` selects a Workbench page; selecting an entity clears that page and stale reply selection. A pending jump sets exact `interaction` or `input`. A reply jump sets `reply`. Refresh never seeds fake entities or clears unread solely because a Session ID is selected.

`workbench.preferences` and `workbench.savePreferences` persist `theme` (`light`, `dark`, `system`), `sidebarOpen`, `inspectorOpen` and `inspectorWide` for the authenticated principal. The names describe the right region, not Files: any panel type installed there follows the same switch and width. Reading a record written before the rename maps the legacy `filesOpen`/`filesWide` fields onto the new ones and falls back per field, so an upgrade keeps the user's theme and switches instead of resetting them; writes always use the current schema, and a stale client submitting the old payload receives the existing refresh requirement. Theme changes mutate tokens without remounting Session, composer or the installed sections. Compact drawer visibility is local to its viewport; durable desktop preferences remain intact. The right column is a drawer below 1150px and the left rail a drawer below 800px; both return focus to their switch on Escape and never open together. The right region's dock layout (open panes, tabs, floats, fullscreen) is browser-local per Session and never crosses devices; layout preferences above remain server-persisted. Settings is a full-window layer in the dsh/ZCode shape: a grouped left navigation (built-in 外观 plus every installed `aork.settings.sections@1` contribution) beside a rounded panel with a centered content column; plugin settings remain plugin-contributed views. End Run and handoff controls are mounted through the public Session actions child in the More menu; the Session archive entry has been removed from the interface entirely (the backend command remains dormant and no UI offers it). The Files provider accepts the public `FilesViewContext` panel/wide presentation hint: normal panels stack tree over preview, wide panels place them side by side, and narrow panels retain selection while switching between tree and preview. No browser Notification permission prompt is used; notification presentation is in-app.

## Verification boundary

Tests use a real Host, installed plugins, SQLite, public authenticated HTTP/snapshots/events and Chromium. Only the external native ACP peer is controlled. The independent UI fixture is separately built and installed with a fixed Host artifact, replacing the whole layout plus messages/menu/notifications; a child crash preserves unread and usable siblings. Two further fixtures prove the region split: one contributes a section to each of the left, centre and right regions through the public targets while the default regions keep working, and one replaces only `aork.workbench.inspector@1` while the default layout, left region and centre stay selected. This is presentation/plugin integration evidence, not real Claude/Codex acceptance. Native history replay is a stated producer invariant and gets actual recovery coverage in ticket 23.

The accepted integration keeps original Inputs migration4 and Reconciliation migration5 and appends Replies as migration6. Native history migration7 is reserved for the later recovery ticket. Session input options/extensions, protected active/queued previews, omitted-detail summaries and the exact `sessions.turn` original-input resource remain owned by Sessions. Completed reply IDs are derived after the final timeline compaction; the owner reserves their bounded UUID-summary charge within the same 900k DTO budget. An incomplete compact response cannot acquire a complete-content read watermark, while its immutable pages remain independently available.
