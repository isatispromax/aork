# Text Turns, streamed history and cancellation

The `sessions` Plugin owns queued input, Turns, user/Agent timeline and display-only tool reports. `runtime-acp` owns ACP requests, operation intents, durable facts and live response channels. `interactions` owns the pending permission projection. All three use public SDK services and owner repositories; no Plugin reads another Plugin's SQL or stores a native deferred/context in SQLite.

## Public interfaces

| Interface | Behavior |
| --- | --- |
| `sessions.sendText` | Authenticated durable command `{sessionId,text}`. Returns the original queued Turn receipt; it does not claim the Agent completed or received the prompt. |
| `sessions.removeQueuedTurn` | Durable `{turnId}` command. Removes only a queued input with a retained `removed` tombstone; dispatched/terminal input rejects with409. |
| `sessions.continueQueue` | Durable `{sessionId,runId,allowNewContext?}` command. Only the current Host-owned ready Run may continue. Cross-Run queued input additionally requires explicit `allowNewContext:true`; this never resends terminal or uncertain Turns. |
| `sessions.cancelTurn` | Authenticated durable command `{turnId}`. An accepted, undispatched input can be cancelled immediately. A dispatched Turn becomes cancelling until its actual terminal outcome. |
| `sessions.overview` / `sessions.detail` | Session execution, active prompt (or latest terminal) `currentTurn` and persistent `dispatchPaused`. |
| `GET /api/resources/sessions.timeline?sessionId=<uuid>` | Authorized bounded Turn/message/tool history, including archived Sessions. `truncated` explicitly reports a shortened view; persisted history is not deleted. |
| `GET /api/queries/interactions.pending` | This principal's currently valid pending permission requests, correlated by Session, Run, generation, Turn, native Session and typed request ID. |

Send/cancel use the existing Origin, Cookie, CSRF, current graph and versioned command envelope. Identical principal/command ID/content returns the same immutable receipt before current busy/reference checks, including after completion. Changed content conflicts. User whitespace and Unicode are content; trim only determines whether input is empty. Input is limited to 16,000 UTF-8 bytes and 24,000 serialized JSON string bytes, leaving durable event headroom. Invalid input leaves no receipt or partial message.

A single short transaction stores a queued Turn, exact user message, owner event and immutable receipt. `acceptanceOrder` is a persistent database acceptance ordinal, independent of wall-clock timestamps. A separate short scheduling transaction claims the earliest queued Turn by compare-and-set, appends its Runtime prompt intent and publishes its Sessions-owned dispatching event atomically. Runtime rechecks the current Run and stop intent, commits attempting, then issues the actual ACP `session/prompt`. Only one dispatched/running/cancelling prompt reserves a Session. Following inputs are accepted into its visible persistent queue, including while waiting/cancelling or paused when the Run is still ready. At most100 pending inputs are admitted per Session. Queued input can be removed; original input and command receipt remain in history. Queue removal and dispatch serialize through the same writer transaction, so a removal that loses the race returns409 rather than claiming success. New scheduling never changes an immutable command receipt.

## Durable streaming and bounds

SDK notification callbacks are concurrent. Runtime places attributable message/tool/permission progress and the definitive prompt outcome on one per-Run persistence lane. Neither the prompt lifetime nor a permission deferred occupies that lane or Run control. Facts commit before Sessions applies its projection, browser event and consumer offset in one transaction. Late/stale native Session or generation updates cannot select an arbitrary Session.

Text splits at codepoint boundaries, with at most 4,000 UTF-16 code units and approximately 8,000 serialized bytes per fact. Pending ingestion is bounded by 256 frames and 256KiB of charged serialized work. Overflow closes/stops the affected managed Run; unrelated Runs remain usable. The ACP frame limit is 1MiB. The timeline response stays below 900,000 serialized bytes (transport limit1MiB), includes at most150 recent Turns (retaining all at-most100 queued inputs),1,000 messages/200 tools, and trims all collections as needed with `truncated:true`.

Tool calls/patches update a bounded display keyed by native tool ID; text content is bounded and other content gets a safe placeholder. Reports never invoke tools. Raw input/output, `_meta`, Agent thoughts and native error data are not projected. `usage_update` is reported context used/size and optional session cost, not an invented per-Turn token bill. Absent usage/cost is unknown. A definitive native RPC error becomes failed with a code-only reason, distinct from uncertain transport loss.

## Permission response channels and cancellation

A reliable ACP permission request creates a live generation-bound response channel and a durable Interactions projection. Ordinary Agent questions do not create pending work. This slice has no allow/deny/respond command, automatic approval or approval timeout. Requests must fit their schema and a24KiB serialized fact budget before registration. Unsupported/oversized, duplicate or excess channels close their affected connection and use managed stop; they cannot poison terminal persistence. At most16 permission channels remain live.

A public ACP Stream wrapper also bounds **all** incoming RPC requests, including unknown methods, rejected/stale requests and SDK-held responses. It charges typed request IDs and serialized bytes before SDK dispatch (64 pending requests/2MiB), and releases only after the underlying response write completes. Duplicate/malformed requests and overload synchronously close that connection before further responses are queued, then stop the owned process. These are pending-write limits rather than lifetime request counts.

Cancel acceptance persists cancelling, its Runtime control intent and `dispatchPaused:true`, so following queued input cannot start after cancellation. Cancellation, failed/interrupted/uncertain delivery, ending a Run and restart all preserve queue pause. Only explicit `sessions.continueQueue` clears it after current Run/Host/generation checks. Runtime closes new response admission, invalidates/settles existing channels as native cancelled, persists invalidation, then sends semantic `session/cancel`. Notification completion or a local abort is not stop proof. A cooperative original prompt response with stopReason cancelled ends the Turn while preserving ready Run and held Claim. A definitive completion winning the race retains its actual stopReason. If1.5s grace expires, the existing Runner confirms managed stop; the Turn retains that fallback reason and never fabricates an ACP cancelled stopReason.

End Run/shutdown closes channels first, closes ACP and joins prompt/ingestion separately from process-group/job supervision. Fresh Runtime-owned cleanup retries retained invalidations/terminal outcomes when an ordinary or dependent cleanup scope cannot write. Only confirmed Run stop releases a Workspace Claim. Browser disconnect remains observation-only.

## Loss, restart and validation

An attempted prompt with no durable attributable Agent progress or definitive response becomes delivery_unknown on transport loss. Durable text/tool/permission progress followed by lost connection becomes interrupted. No uncertain input is automatically replayed. Critical persistence failure closes intake and stops or blocks affected execution; memory-only output is never presented as saved.

Restart fences old epochs, invalidates old channels and pauses unfinished Session dispatch. Accepted text remains retained. Runtime uses persisted attempting/progress evidence; when Runtime is disabled, Sessions conservatively uses its own durable progress projection to distinguish uncertain delivery from known interruption. Old PIDs are never used as new stop authority. Queued inputs retain their original Run binding. Starting a new Run does not silently adopt them. The public continue command and default UI require an explicit new-native-context decision before rebinding only queued Turns; already attempted inputs are never candidates. Unknown Runs still require the existing local maintenance path before another Run can start. No force-release UI is added.

The default Detail composes independently selected `aork.sessions.composer@1`, `aork.sessions.messages@1` and `aork.sessions.tools@1` providers. The composer guards IME Enter, supports Shift+Enter, retains draft plus original uncertain command ID across browser reload, and follows authoritative states. The default UI consumes public owner snapshots and14 durable event subscriptions. The Sessions overview snapshot omits filesystem observations; the separate async `sessions.environments` query polls physical directory availability without rewriting snapshot state. The timeline snapshot includes the exact DB projection and event cursor. The composer shows ordered pending input, removal, persistent pause and explicit continue, and accepts additional input while a prompt runs. No timer guesses completion. An independently packaged UI replaces all three against a fixed Host build and the same public service constraints.

Acceptance is local macOS with actual Node24.22.3, built Plugins, Runner processes, SQLite, HTTP/events/local maintenance and Chromium. Only the external ACP Agent/timing/fault process is controlled. This is not real Claude/Codex, Linux, remote deployment, native recovery, MCP execution or structured-input acceptance.
